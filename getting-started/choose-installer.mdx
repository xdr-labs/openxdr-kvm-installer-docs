# Choose an Installer

Use the deployment target, expected topology, and performance model to select one installer. Each script is stateful and menu-driven, but its VM topology and host changes are different.

| Installer | Use it for | Current step count |
| --- | --- | ---: |
| `DP-Installer.sh` | Standalone Data Processor with DL-master and DA-master | 14 |
| `Sensor-Installer.sh` | Standard modular Sensor | 10 |
| `6000-Sensor-Installer.sh` | High-performance dual-VM / NUMA-oriented Sensor | 10 |
| `AIO-Sensor-Installer.sh` | Integrated AIO Data Processor + Sensor | 13 |

## Decision guide

<Steps>
  <Step title="Need DL and DA Data Processor VMs?">
    Use **DP-Installer.sh**. It includes DP image preparation, DL/DA deployment, SR-IOV/CPU-affinity work, appliance CLI installation, and a final NFS backup configuration step.
  </Step>
  <Step title="Need only a standard modular Sensor?">
    Use **Sensor-Installer.sh**. It prepares the host, creates Sensor storage, deploys the Sensor VM, and configures Sensor networking/SPAN connectivity.
  </Step>
  <Step title="Need a higher-throughput Sensor topology?">
    Use **6000-Sensor-Installer.sh**. This path is designed around dual Sensor VMs and NUMA-aware placement, with PCI passthrough for SPAN traffic.
  </Step>
  <Step title="Need AIO and Sensor on one KVM host?">
    Use **AIO-Sensor-Installer.sh**. It prepares AIO storage and image, deploys the AIO VM, then creates and deploys the Sensor path on the same host.
  </Step>
</Steps>

<Note>
Do not mix state files from different installer families on the same installation workflow. Run the script that matches the intended topology and keep its state/configuration together.
</Note>
